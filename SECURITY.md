# Безопасность sales-dashboard

Живой документ: модель угроз, что закрыто, что осталось. Обновлять при изменениях
в авторизации, хостинге или доступах.

## Что защищаем

Коммерческие данные сети «Мария»: план/факт/маржа по 21 точке, себестоимость,
выручка по каналам, база карт лояльности, телефоны клиентов (SMS-аудитории),
бюджеты рекламы. Утечка = данные конкурентам (Стефания, Этика, Cake Home, ЯХОНТ)
и персональные данные покупателей.

## Контур доступа (после 30.07.2026)

| Уровень | Чем открывается | Что даёт |
|---|---|---|
| Публично | — | `/api/health`, статика (HTML/CSS/JS) |
| PIN-сессия | `DASHBOARD_PIN` → cookie `maria_session` (8 ч, HttpOnly, SameSite=Strict) | все данные-API, дашборд, аналитика, маркетинг, производство |
| Админ-токен | `X-User-Token` (cookie/заголовок) | то же + `/api/admin/*`, персональные данные клиентов, экспорт аудиторий |
| Машинный | `X-API-Key` на `/api/ingest/*` | приём данных из 1С |
| maria-app | HMAC-подпись `phone:ts` на `/api/app-bridge/*` | баланс баллов по верифицированному телефону |

**Главный инвариант:** новый роут `/api/*` закрыт ПО УМОЛЧАНИЮ — гейт стоит в одном
месте (начало обработчика в `api/server.js`), а не «не забыть навесить requireSession».
Публичное — только явный белый список `PUBLIC_API_EXACT` + `isPublicApiPath()`.

## Закрытые уязвимости (30.07.2026)

1. **PIN-гейт был только клиентским.** `requireSession` стоял на 3 роутах из 85 —
   `curl` без авторизации отдавал `/api/dashboard/summary` (план/факт/маржа),
   `/api/analytics/sales`, `/api/marketing/*`, `/api/metadata`. Закрыто глобальным гейтом.
2. **Порт 3000 торчал в интернет.** node слушал `0.0.0.0` при том, что nginx
   проксирует на `127.0.0.1:3000` → можно было ходить в API мимо nginx.
   Теперь `HOST=127.0.0.1` (в docker — `0.0.0.0` через ENV).
3. **Админ-токен утекал в логи nginx** (300 записей `?userToken=…`).
   `access.log` переведён на формат без query-string.
4. **Нет заголовков безопасности.** Добавлены `nosniff`, `no-referrer`,
   `X-Frame-Options: DENY`, COOP, `Permissions-Policy`; CSP на HTML
   (внешних origin у проекта нет, `eval` не используется).
5. **SSH-брутфорс VDS** (~18 тыс. попыток/мес): fail2ban (5 попыток/10 мин → бан 2 ч)
   + вход по ключу.

## Что уже было в порядке

- PIN сверяется `crypto.timingSafeEqual`, есть rate-limit по IP на `/api/auth`.
- Админские роуты и персональные данные клиентов требовали токен и до правок.
- Cookie: HttpOnly + SameSite=Strict, `Secure` автоматически при HTTPS.
- Подключение к Postgres шифруется (TLS).
- Секретов в git нет (только `.env.example`).

## Осталось (требует решения владельца)

1. **HTTPS.** Дашборд работает по HTTP на голом IP → PIN и токены идут по сети
   в открытом виде; перехват возможен в чужой Wi-Fi/сети провайдера.
   Вариант «в лоб» — сертификат на `*.sslip.io`, НО такие домены РКН режет
   по SNI из бытовых РФ-сетей (проверено на VPN-панели 14.07.2026) → риск
   потерять доступ с рабочих мест. Надёжно — свой домен (~1–2 тыс. ₽/год)
   + Let's Encrypt; certbot на VDS уже стоит.
2. **Ротация админ-токена.** Текущий светился в URL, логах и переписке.
   Не ротировал сам, чтобы не отрезать сохранённые ссылки — по команде меняю
   (обновить: `.dashboard-vds-info`, утренний дайджест, память).
3. **PIN 6 цифр** — с rate-limit достаточно, но общий на всех: нет учёта «кто входил».
   При росте числа сотрудников — заводить пользователей с токенами.
4. **xlsx (SheetJS) ReDoS**, фикса от вендора нет. У нас библиотека только
   ГЕНЕРИРУЕТ файлы, не парсит пользовательские → эксплуатация не применима.
   Пересмотреть, если появится импорт файлов от пользователей.
5. **Postgres TLS без проверки сертификата** (`rejectUnauthorized: false`) —
   шифрование есть, защиты от MITM внутри ДЦ Timeweb нет.

## Правила для будущих правок

- Новый роут с данными — НИЧЕГО не делать: гейт закроет сам. В белый список
  добавлять только с обоснованием в этом файле.
- Секреты — только в `.env` на сервере (perm 600), никогда в git и не в URL.
- Токены не передавать в query — только заголовком или cookie.
- Перед мержем правок авторизации: `curl` без токена по 3–4 «жирным» роутам
  должен вернуть 401, а вход по PIN в браузере — показать данные.
