# Инструкция: интеграция 1С УПП с дашбордом продаж

## Что нужно сделать

Настроить автоматическую отправку данных о продажах и планах из 1С УПП
на сервер дашборда раз в час. Дашборд обновляется в реальном времени.

---

## Источники данных (точно от заказчика)

### 1. Розничные точки — продажи

- **Регистр**: `РегистрНакопления.ВаловаяПрибыль`
- **Фильтр**: `Склад В ИЕРАРХИИ` группы складов **«Розничные склады Мария»**
- **Поля**: `ВыручкаОборот`, `СтоимостьОборот`, `КоличествоОборот`,
  измерения `Склад` и `Номенклатура`
- На дашборде эти точки появляются как обычные магазины (region: «Иркутск»).

### 2. Опт / онлайн / B2B — продажи

- **Регистр**: `РегистрНакопления.ВаловаяПрибыльУпр` (управленческий)
- **Фильтр**: `Подразделение В` списке из 6 подразделений:
  1. Агрегатор
  2. Опт
  3. Отдел интернет продаж
  4. Отдел Интернет продаж Ангарск
  5. Отдел Продаж ЗП
  6. Корпоративные клиенты
- На дашборде эти 6 подразделений отображаются как отдельные «точки»
  с region: «Управленческий».

### 3. Опт / онлайн / B2B — план

- **Источник**: документ **«Установка план-факт»** по тем же 6 подразделениям
- Документ должен делать движения в регистр накопления (в шаблоне
  по умолчанию подставлено `РегистрНакопления.ПланыПродаж` —
  это нужно проверить).

> ⚠️ План для розничных точек в этой версии не выгружается. Если он нужен —
> добавьте отдельный запрос (см. внизу).

---

## Шаг 1 — Создать общий модуль

В конфигураторе:

**Конфигурация → Общие → Общие модули → (правая кнопка) Добавить**

Параметры модуля:
- Имя: `ДашбордПродаж`
- Флаги: ✅ Сервер, ✅ Вызов сервера

Скопировать в модуль содержимое файла:
```
examples/upp-http-export-template.bsl
```

---

## Шаг 2 — Что нужно проверить разработчику 1С

В шаблоне есть три запроса. Каждый обёрнут в `Попытка/Исключение` —
если что-то не так, ошибка будет в окне сообщений, выгрузка не упадёт целиком.

### 2.1. Запрос `ПолучитьПродажиРозница`

| Что проверить | Как |
|---|---|
| Имя группы складов | В коде задано `НаименованиеГруппыРозницы = "Розничные склады Мария"`. Открыть справочник «Склады», найти эту группу. Если имя другое — поправить в коде. |
| Имя регистра | `РегистрНакопления.ВаловаяПрибыль`. Открыть конфигуратор → Регистры накопления — должен быть. |
| Имена ресурсов | `ВыручкаОборот`, `СтоимостьОборот`, `КоличествоОборот`. В типовой УПП 1.3 — стандарт. В кастомных могут быть `СуммаВыручкиОборот` и т. п. — поправить. |
| Измерение Склад | В регистре `ВаловаяПрибыль` должно быть измерение `Склад`. В некоторых конфигурациях оно отсутствует — там есть только `Подразделение`. Тогда либо заменить `Склад` на `Подразделение` и фильтр на список складов-подразделений, либо использовать вариант с управленческим регистром. |

### 2.2. Запрос `ПолучитьПродажиУпр`

| Что проверить | Как |
|---|---|
| Имя регистра | По умолчанию `РегистрНакопления.ВаловаяПрибыльУпр`. В кастомных бывает `ВаловаяПрибыльУправленческий`. Поправить если нужно. |
| Наименования подразделений | Список в функции `НайтиПодразделенияПоИменам()`. Должно совпадать **по символам** с полем `Наименование` в справочнике «Подразделения» (регистр, пробелы, кавычки). При запуске функция выводит сообщения о тех, что не нашлись. |
| Группа vs элемент | В справочнике подразделения могут быть как группы. В шаблоне ищем только листовые элементы (`ЭтоГруппа = ЛОЖЬ`). Если какое-то подразделение из списка — это группа, поменять условие. |

### 2.3. Запрос `ПолучитьПланУпр`

Это самый рискованный запрос — точное место хранения плана зависит от
конкретной конфигурации.

| Что проверить | Как |
|---|---|
| Имя документа | «Установка план-факт». Открыть справочник документов в конфигураторе. Возможные имена объекта: `УстановкаПланФакт`, `УстановкаПланаФакт`, `ПланФакт`. |
| Куда документ пишет данные | В свойствах документа → «Регистрация изменений» / «Движения». Если документ делает движения в регистр накопления — использовать **Вариант A** (по умолчанию). Если данные хранятся только в табличной части — использовать **Вариант B** (закомментирован в коде). |
| Имя регистра в Варианте A | По умолчанию `ПланыПродаж`. Возможные варианты: `ПланыПродажОбъемно`, `ПланыПродажКомплектов`, или собственный регистр. |
| Структура документа в Варианте B | Имя табличной части (по умолчанию `Товары`), имя реквизита подразделения (по умолчанию `Подразделение` на самом документе), имя поля суммы (по умолчанию `Сумма`). |

При запуске запрос выведет сообщение об ошибке — по нему станет
понятно, какой вариант брать.

## Шаг 3 — Создать регламентное задание

**Конфигурация → Общие → Регламентные задания → Добавить**

Параметры:
- Имя: `ВыгрузкаВДашбордПродаж`
- Метод: `ДашбордПродаж.ВыполнитьВыгрузкуВДашборд`
- Использование: ✅ включено

Расписание:
- Повторять каждые: **3600 секунд** (1 час)
- Или: каждый день в 07:00, 10:00, 13:00, 16:00, 19:00

## Шаг 3.5 — Залить историю за прошлые месяцы (РАЗОВО)

После того как ручной запуск `ВыполнитьВыгрузкуВДашборд()` отработал
чисто, нужно ЗА ОДИН РАЗ залить историю — чтобы на дашборде заработали:
- сравнение «vs прошлый месяц»
- сравнение «год к году»
- тренд по месяцам
- AI-анализ сезонности

В шаблоне для этого есть отдельная процедура:

```bsl
ДашбордПродаж.ВыгрузитьИсторию(24);
```

Аргумент — сколько месяцев назад выгрузить (по умолчанию 24). Запустить
ОДИН РАЗ в нерабочее время или в выходные. Каждый месяц = 3 запроса
к регистрам 1С + один POST на сервер. На 24 месяца ~5–10 минут.

Можно прерывать — повторный запуск безопасен (на сервере дедупликация
по хэшу пакета). Если какой-то период не получится — будет сообщение
с ошибкой, остальные дойдут.

После выполнения в селекторе периода на дашборде появятся все
выгруженные месяцы.

---

## Шаг 4 — Проверить вручную

Перед запуском по расписанию:

1. Открыть **Сервис → Консоль функций** или другой способ запустить код на сервере
2. Выполнить:
```bsl
ДашбордПродаж.ВыполнитьВыгрузкуВДашборд();
```
3. В окне сообщений — должны быть:
   - Если что-то не нашлось/упало: понятные сообщения о причине
   - В конце: ответ сервера вида `{"ok":true,"run":{"status":"success",...}}`

При первом запуске будет видно, какие из 6 подразделений найдены
и нашлась ли группа складов.

## Параметры сервера

| Параметр | Значение |
|---|---|
| URL | `https://sales-plan-dashboard.onrender.com/api/ingest/upp` |
| API-ключ | `85307b26064e3764b0b19ce3223353057b0fe754b31f0f3a` |

Тип `URI` в 1С доступен только в мобильном приложении и недоступен на сервере —
поэтому в `ОтправитьPOST()` хост и путь прописаны явно.

---

## Что происходит после отправки

- Данные сохраняются в PostgreSQL на сервере
- Дашборд в браузере обновляется автоматически (без перезагрузки)
- Каждая отправка логируется — `/api/ingest/runs`
- Повторная отправка одного и того же пакета безопасна (дедупликация по хэшу)

---

## Если нужно добавить план для розничных точек

В шаблоне `ПолучитьПланУпр()` берёт план только по управленческим
подразделениям. Если нужен план и для розничных магазинов — добавить
вторую функцию `ПолучитьПланРозница()` по аналогии:
запрос к тому же регистру плана, но с фильтром
`Склад В ИЕРАРХИИ (&ГруппаРозницы)`. И объединить результаты в
`СформироватьПланы()`.
